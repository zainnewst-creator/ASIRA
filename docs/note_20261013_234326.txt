ASIRA RESEARCH LEARNING PLATFORM

PHASE 3 — FINAL SECURITY VALIDATION, GAP REMEDIATION & PRODUCTION READINESS

1. Mission

Project: ASIRA Research Learning Platform (منصة أسيرا لتعليم البحث العلمي)

You are continuing an existing application after:

- Phase 1: Project inspection, safe cleanup, TypeScript/build fixes, and initial regression checks.
- Phase 2: Reported security hardening of Firestore Rules, exam grading, role authorization, certificates, URL sanitization, audit records, and security-related code.

Phase 2 reported successful TypeScript validation and production builds, but this does not independently establish that the application is secure or production-ready.

Your mission is to perform the final independent validation, close remaining security gaps, add missing automated tests, verify GitHub/Vercel/Firebase deployment readiness, and produce evidence-based release recommendations.

Do not rebuild the application. Do not blindly repeat completed work. Do not claim that the platform is 100% secure.

Work only on the existing project, preserving its architecture, functionality, educational workflows, Arabic/English support, and RTL experience.

The final objective is a demonstrably tested and deployable application with clearly documented residual risks.

2. Mandatory Safety Rules

Before changing anything:

1. Inspect the repository, current branch, Git status, recent commits, package files, environment configuration, and project documentation.
2. Identify all uncommitted changes. Never overwrite, discard, reset, or silently replace work from previous phases.
3. Preserve the existing "phase-2-security-hardening" branch and its history.
4. Create a dedicated Phase 3 working branch only after confirming the current Git state and selecting a safe branching strategy.
5. Never expose secrets in terminal output, reports, screenshots, test logs, or generated files.
6. Never print actual API keys, access tokens, passwords, private credentials, service-account private keys, or complete sensitive environment files.
7. Do not run destructive tests against production data or production services.
8. Use Firebase Emulator Suite or an isolated test project for authorization, database, and integration testing wherever possible.
9. Never deploy to production, change live access permissions, rotate production credentials, delete production data, or modify production infrastructure without explicit authorization.
10. Do not create paid infrastructure or enable paid services without authorization.
11. Do not upgrade or replace major dependencies blindly. Evaluate compatibility, security impact, and regression risk first.
12. Never suppress a security issue merely to make tests pass.
13. Never weaken Firestore Rules, disable security checks, or add permissive fallback rules to restore broken functionality.
14. If a test cannot safely or technically be performed, mark it "NOT TESTED" or "BLOCKED" and explain why.
15. Do not invent test results, coverage figures, vulnerability findings, or deployment status.

Before every significant remediation, identify the root cause and the smallest safe correction.

5. Firestore Security Rules — Independent Adversarial Testing

Review the actual current "firestore.rules" and validate the effective authorization behavior using the Firebase Emulator Suite where feasible.

Do not merely repeat the previous line-by-line review.

Create or extend automated tests covering:

A. Identity and ownership

- Unauthenticated users attempting protected reads and writes.
- A student reading another student's private profile.
- A student modifying another user's profile.
- A student changing ownership fields such as "uid", owner ID, or enrollment identifiers.
- An instructor accessing a course they do not teach.
- An instructor accessing unrelated students or courses.
- A user attempting to gain access by changing client-side state or request fields.
- Cross-user and cross-course document access.

B. Privileged roles

- Students attempting to become instructors or administrators.
- Users attempting to modify their own role, permissions, approval status, or privileged claims through client-accessible paths.
- Users forging role fields in request bodies.
- Users attempting to modify trusted role-assignment records.
- Deleted, disabled, or otherwise unauthorized accounts attempting privileged operations, where the configured architecture supports these states.

Verify whether authorization relies on trusted server-issued claims, securely controlled database records, email-based checks, or combinations of these mechanisms.

Email verification must not be treated as a substitute for trusted role assignment.

If administrator authorization has an email-based fallback, determine whether that fallback can independently grant administrative access. Eliminate insecure fallback paths if present, while preserving the legitimate administrator workflow.

Do not invent an administrator email or credentials.

C. Field-level authorization

Test unauthorized changes to:

- Grades and calculated scores.
- Official and practical grades.
- Approval and completion states.
- Course membership.
- Instructor assignments.
- Certificate issuance status.
- Audit actor identity and role.
- Administrative metadata.
- Created/updated timestamps and ownership fields.
- Any other sensitive fields discovered in the actual schema.

Test both forbidden-field injection and unauthorized updates to existing documents.

D. Query and document-level access

Test whether security rules correctly enforce access for:

- Direct document reads.
- Collection queries.
- Nested subcollections.
- Alternate document IDs.
- Unexpected but valid query patterns.
- Documents with missing or malformed ownership fields.

Remember that Firestore Rules are not ordinary post-query filters. Confirm that authorized queries can actually satisfy the rules without requiring insecure changes.

E. Data validation

Check enforcement of:

- Required fields.
- Allowed field sets.
- Data types.
- Valid enum values.
- String and array length limits.
- Numeric ranges.
- Valid state transitions.
- Immutable fields.
- Timestamp constraints where relevant.
- Unexpected nested objects and additional fields.

Use "hasOnly", "hasAll", "diff().affectedKeys()", or equivalent appropriate mechanisms when necessary and compatible with the existing design.

Do not rely on frontend validation for authorization or integrity.

F. Security Rules test matrix

For each important collection and operation, cover:

- Anonymous user.
- Student acting on their own data.
- Student acting on another user's data.
- Authorized instructor.
- Unauthorized instructor.
- Administrator.
- Malicious authenticated user attempting privilege escalation.

Add missing automated tests using the repository's existing testing framework or the appropriate Firebase Rules testing libraries.

Run the tests against the emulator. Do not claim emulator verification unless the tests actually ran successfully.

6. Trusted Grading and Examination Integrity

This is a release-critical area.

Inspect the complete exam lifecycle, from authoring through submission and final grade display.

A. Answer-key confidentiality

Verify that students cannot retrieve correct answers, scoring weights, hidden explanations, answer keys, or equivalent sensitive data through:

- Firestore reads.
- Nested documents.
- Client-side query responses.
- Exam objects returned by services.
- Publicly bundled frontend assets.
- Debug output or logs.
- Alternate API or backend responses.

Inspect the actual data returned to students rather than relying exclusively on "sanitizeExamForStudent".

A frontend sanitizer is not an authorization boundary.

B. Grade calculation and persistence

Determine exactly where official exam grades are calculated.

Verify that the authoritative grade cannot be supplied or modified by an untrusted client.

Test attempts to:

- Inject "score", "grade", "officialGrade", or "calculatedScore".
- Modify grade fields after submission.
- Change submission status to a privileged state.
- Alter exam identifiers or ownership.
- Replay submissions.
- Submit another student's answers.
- Modify a previously graded attempt.
- Forge grading metadata or grader identity.
- Bypass required validation by using alternate document IDs.

If grading is performed only on the client, document the trust-boundary weakness.

Where necessary and compatible with the existing architecture, implement or prepare a trusted grading path using an existing trusted backend or an appropriate secured server-side component.

Do not add an expensive service or change the application's architecture unnecessarily.

If a secure server-side grading implementation is necessary but cannot be completed safely, mark the feature as a release blocker rather than pretending Firestore Rules alone solve the issue.

C. Attempts, timing, and replay

Inspect how the platform manages:

- Exam start time.
- Submission deadlines.
- Attempt limits.
- Repeated submissions.
- Concurrent submissions.
- Resuming interrupted exams.
- Duplicate requests.
- Final submission state.
- Server-authoritative timestamps.
- Exam availability and enrollment eligibility.

Test concurrent or repeated submissions where feasible.

A client-generated timestamp must not be treated as authoritative proof of submission time.

Determine which controls can actually be enforced with the existing architecture. Do not claim that a browser-based timer prevents all cheating.

D. Practical grades and assignments

Test whether a student can:

- Assign their own practical grade.
- Change "gradedBy" or "gradedAt".
- Alter a finalized practical grade.
- Submit work on behalf of another student.
- Change the ownership of a submission.
- Modify an approved assignment.
- Access another student's submitted file.

Confirm that only the authorized instructor or administrator can perform the intended grading actions.

10. HTTP Security Headers and Deployment Configuration

Inspect the actual response headers produced by the configured hosting platform.

Do not assume HTML meta tags provide equivalent protection to HTTP response headers.

Check the relevant hosting configuration, such as "vercel.json" or equivalent existing deployment configuration.

Where compatible with the application, evaluate and configure appropriate headers:

- "Content-Security-Policy".
- "X-Content-Type-Options".
- "Referrer-Policy".
- "Strict-Transport-Security" for the HTTPS production domain.
- "frame-ancestors" through CSP or another appropriate framing control.
- "Permissions-Policy".
- Appropriate cache controls for sensitive responses, where applicable.

Do not blindly add headers that break Firebase authentication, legitimate embedded resources, or required third-party integrations.

For CSP:

1. Inventory the actual scripts, styles, fonts, images, API connections, and other required origins.
2. Create a policy compatible with the real application.
3. Prefer restrictive policies.
4. Avoid unsafe exceptions unless their necessity is established.
5. Test the policy against actual application workflows.
6. Report any remaining exceptions.

Do not expose secrets or use source-code modifications as a substitute for server-side header configuration.

If a real production domain is not available, validate the deployment configuration statically and mark live header verification as "BLOCKED" or "NOT TESTED".

26. Release Decision Criteria
Use the following decision categories:
RELEASE BLOCKED
Use this when a material unresolved issue could permit unauthorized access to sensitive student data, privilege escalation, grade manipulation, answer-key disclosure, certificate forgery, secret exposure, or another serious compromise.
Also use it when a critical trust boundary has not been implemented or cannot be adequately verified.
CONDITIONAL RELEASE
Use this only when no known critical or high-risk unresolved issue remains, essential controls have been verified, and the remaining limitations are explicitly documented and accepted by the project owner.
State all required conditions.
READY FOR AUTHORIZED DEPLOYMENT
Use this only when:
No known unresolved critical or high-severity security issue remains.
Essential authorization and grading controls have been tested.
Relevant security and regression tests pass.
Build and TypeScript checks pass.
Required deployment configuration has been verified.
No unresolved secret exposure remains.
Remaining risks and owner actions are documented.
Production deployment and post-deployment verification steps are defined.
A local build alone cannot satisfy these criteria.
If a required remote configuration or live deployment check is unavailable, state that limitation and choose the appropriate release category.
Never claim that a system is completely secure or free from every vulnerability.

Comprehensive Security Assessment, Penetration Testing & Attack Simulation

1. Mission and Mandatory Requirements

Extend Phase 3 into a comprehensive, evidence-based security assessment of the existing ASIRA Research Learning Platform.

The objective is to identify, safely validate, document, and remediate exploitable vulnerabilities across the application's code, authentication, authorization, database, APIs, cloud configuration, deployment pipeline, dependencies, and business logic.

Do not limit the assessment to common vulnerabilities or previously identified issues.

Think like an experienced application-security engineer conducting an adversarial review of the platform.

Mandatory rules:

- Inspect the existing repository and deployed architecture before choosing tests.
- Test the actual implementation rather than relying on assumptions, checklists, or code appearance alone.
- Do not rebuild the application or remove existing features.
- Preserve unrelated user changes and the existing Git history.
- Use Firebase Emulator, isolated test projects, or explicitly authorized test environments.
- Do not perform destructive testing, uncontrolled traffic generation, attacks against third parties, or unauthorized testing of production.
- Do not expose real student data, credentials, tokens, API keys, or other secrets in reports.
- Never report a vulnerability as fixed or verified without appropriate evidence.
- Do not claim complete security or zero vulnerabilities.

2. Build an Attack Surface Inventory

Inspect the repository and identify every applicable attack surface, including:

- Public and authenticated routes.
- Student, instructor, administrator, and super-administrator functionality.
- Firebase Authentication flows and account lifecycle.
- Firestore collections, documents, nested collections, queries, and security rules.
- Firebase Storage buckets and upload/download flows, if present.
- Cloud Functions, callable functions, scheduled jobs, HTTP endpoints, and other backend services, if present.
- Certificate generation and public certificate verification.
- Exam creation, answer delivery, exam attempts, automatic grading, manual grading, and result publication.
- Course enrollment, progress, completion, and access control.
- File import/export, backup/restore, and administrative data operations.
- Search, rich-text rendering, external links, and user-controlled URLs.
- Environment variables, client-side configuration, build artifacts, and source maps.
- GitHub repository settings, CI/CD workflows, Vercel configuration, and deployment secrets, where accessible.
- External services and plugins discovered in the actual implementation.

Produce an attack surface inventory and map each entry to its relevant trust boundaries, permissions, and security controls.

Do not assume a feature or service exists simply because it appears in this checklist.

3. Authentication, Identity, and Account Security

Investigate:

- Weak or missing authentication checks.
- Account enumeration and information leakage.
- Brute-force protection and credential-stuffing resistance.
- Password reset and email-verification abuse.
- Authentication state inconsistencies and stale sessions.
- Token expiration, revocation, misuse, and inappropriate trust in client-supplied identity claims.
- Account takeover paths involving weak recovery or verification flows.
- Duplicate accounts, account deletion, and re-registration edge cases.
- Unauthorized access following role changes, account suspension, or deletion.
- Insecure handling of privileged accounts.
- Trust in email addresses, user profiles, local storage, or client-side flags as proof of authorization.
- Missing server-side verification of Firebase ID tokens where a trusted backend is involved.

Verify whether a user who loses a role or has an account disabled immediately loses the corresponding privileges across all relevant access paths.

Do not treat email verification alone as sufficient authorization to become an administrator.

4. Authorization and Access-Control Attacks

Test for:

- Broken Access Control.
- IDOR and BOLA.
- Horizontal privilege escalation between users.
- Vertical privilege escalation from student to instructor or administrator.
- Broken Function-Level Authorization.
- Missing authorization on individual documents and nested collections.
- Unauthorized access through alternate queries or collection-group queries.
- Unauthorized reads, writes, updates, and deletes.
- Mass assignment and unauthorized modification of protected fields.
- Trust in client-supplied UIDs, roles, ownership identifiers, or tenant identifiers.
- Inconsistent authorization between the UI, Firestore Rules, and backend functions.
- Permission bypass through alternate application routes or direct API requests.
- Data exposure through error messages, exports, backups, and administrative endpoints.

Construct a role-and-resource authorization matrix.

Test every relevant operation for each role and for unauthenticated users. Include attempts to access another user's records by changing identifiers and submitting requests directly rather than using the UI.

Verify authorization independently of whether the frontend hides a button or page.

5. Firestore and Database Security

Review Firestore Rules and validate their behavior with automated tests.

Test:

- Default-deny behavior for unmatched paths.
- Cross-user reads and writes.
- Privilege escalation through user-controlled role fields.
- Unauthorized modification of ownership, grades, roles, timestamps, and audit fields.
- Partial updates that modify protected fields.
- Unexpected fields and malformed data.
- Type confusion, boundary values, oversized values, and unexpected document structures.
- Missing validation of relationships between documents.
- Unauthorized nested-document and collection-group access.
- Query authorization and data exposure through permitted queries.
- Deletes, recreations, and ownership changes.
- Rule conditions that behave differently for missing fields, null values, or unexpected types.
- Reliance on application-side validation when database-side enforcement is required.
- Excessive data access and opportunities for resource or cost exhaustion.

Pay particular attention to any Firestore Rules that permit broad access based on a generic instructor or administrator check.

Confirm that an instructor's permissions are restricted to the courses, students, and records they are actually authorized to manage.

Use Firebase Emulator tests wherever possible. Do not modify production data to prove a vulnerability.

6. Examination, Grading, and Certificate Integrity

Treat the platform's educational records as high-value assets.

Test whether a student can:

- Obtain correct answers or hidden answer keys before an exam.
- Modify scores, grades, completion status, or attempt counts.
- Submit answers on behalf of another student.
- Bypass attempt limits or examination availability windows.
- Replay submissions or create duplicate attempts.
- Manipulate client-side timers or timestamps.
- Exploit concurrent requests to bypass limits or submit conflicting results.
- Access another student's submissions or feedback.
- Modify instructor-assigned grades or grading metadata.
- Forge practical assessment results.
- Obtain certificates without meeting completion or grading requirements.
- Forge certificate identifiers or exploit predictable verification codes.
- Reactivate revoked or invalidated certificates.
- Exploit discrepancies between certificate records and public verification results.

Verify where authoritative grading occurs.

If grading is performed entirely on the client, document the resulting integrity risk and determine the safest compatible remediation. Do not assume that preventing a "score" field in Firestore Rules makes client-calculated scores trustworthy.

7. API and Backend Security

For every discovered API, Cloud Function, or backend endpoint, inspect:

- Authentication and authorization enforcement.
- Trust in caller-supplied identities and roles.
- Input validation and schema enforcement.
- Injection vulnerabilities relevant to the actual implementation.
- Unsafe deserialization or parsing.
- Excessive request payloads.
- Missing request-size limits.
- Resource-intensive operations.
- Insecure error handling and information leakage.
- Replay and duplicate-request handling.
- Race conditions and concurrent state changes.
- Insecure direct references to database documents or external resources.
- Missing quotas, rate limits, or abuse controls.
- Improper handling of upstream service failures.
- Secrets exposed in responses, logs, or exceptions.

Do not invent APIs that do not exist. If the application has no traditional backend, explicitly assess the security implications of its client-to-Firebase architecture.

8. Injection and Browser-Side Attacks

Assess applicable variants of:

- Reflected, stored, and DOM-based Cross-Site Scripting (XSS).
- HTML injection.
- JavaScript injection.
- SQL or NoSQL injection, where relevant to the actual data-access stack.
- Command injection, if operating-system commands are invoked by any component.
- Template injection, if a relevant template engine exists.
- Path traversal and unsafe file path handling.
- Open redirects.
- Unsafe URL schemes and external-link handling.
- Content injection through course descriptions, announcements, submissions, and rich-text content.
- Prototype pollution and unsafe object merging, where applicable.
- Insecure DOM manipulation and unsafe HTML rendering.
- Malicious SVG or HTML uploads, if these formats are accepted.
- Content Security Policy gaps and other relevant browser security weaknesses.

Use harmless test payloads in the authorized test environment. Do not execute destructive payloads or access unrelated systems.

Review "sanitizeInput", "sanitizeUrl", "isTrustedStorageUrl", and related utilities to establish whether they are used correctly at security-sensitive sinks. Do not assume that a sanitizer's existence proves that the application is protected.

9. File, Storage, and Upload Security

If uploads or Firebase Storage are present, test:

- Unauthorized upload, download, overwrite, and deletion.
- Cross-user and cross-course file access.
- Incorrect MIME-type and extension validation.
- Oversized files and resource exhaustion.
- Path traversal and unsafe filenames.
- Public exposure of private educational records.
- Reuse or leakage of download tokens and signed URLs.
- Insecure object ownership and permission inheritance.
- Malicious file content and unsafe browser rendering.
- Inadequate retention and deletion behavior.

Verify actual storage rules and access permissions.

Do not upload malware or conduct destructive file tests.

10. Availability, Abuse Resistance, and Cost Security

Evaluate resilience against:

- Application-level denial of service.
- Distributed denial-of-service exposure and dependence on provider-level protections.
- Brute-force and automated abuse.
- Rate-limit bypass.
- Excessive Firestore reads, writes, and queries.
- Repeated invocation of expensive functions.
- Unbounded loops or computationally expensive operations.
- Oversized requests and unusually large documents.
- Abuse of authentication, email, notification, and external-service workflows.
- Repeated certificate verification or export requests.
- Automated account creation and other abuse relevant to the platform.

Use bounded tests in an isolated environment with explicit request limits and stop conditions.

Inspect actual hosting-provider protections, quotas, monitoring, and configuration where authorized.

Do not perform uncontrolled load tests or claim DDoS protection based on local tests alone.

Assess whether an attacker could cause significant unexpected usage or financial costs, and recommend practical controls such as quotas, limits, monitoring, and alerts.

11. Race Conditions and Business-Logic Exploitation

Look for security failures that occur only through particular sequences of actions.

Examples include:

- Simultaneous exam submissions.
- Duplicate grading operations.
- Concurrent certificate issuance and revocation.
- Repeated course completion requests.
- Account deletion while privileged operations remain in progress.
- Role changes during active sessions.
- Replayed administrative requests.
- Conflicting updates to the same record.
- Time-of-check/time-of-use inconsistencies.
- Operations that partially succeed and leave security-sensitive state inconsistent.

Use controlled concurrency tests in the isolated environment.

Verify whether critical operations are atomic, idempotent where appropriate, and protected against unauthorized state transitions.

12. Cross-Site Request Forgery and Server-Side Request Forgery

Assess CSRF only where the application's authentication mechanism and request architecture make it relevant.

Assess SSRF if any component fetches user-controlled URLs, processes remote resources, or makes server-side HTTP requests.

For SSRF testing, use controlled test endpoints and safe indicators. Do not probe cloud metadata services, internal networks, or third-party systems without explicit authorization.

Document why either category is not applicable when the relevant attack surface does not exist.

13. Secrets, Privacy, and Information Disclosure

Inspect for:

- Credentials, private keys, tokens, and API secrets committed to Git.
- Secrets embedded in client-side bundles or source maps.
- Sensitive environment variables exposed to browser code.
- Excessive Firebase permissions or exposed administrative credentials.
- Personal data returned unnecessarily to clients.
- Sensitive records leaked through logs, errors, backups, exports, or analytics.
- Public access to private course materials, submissions, grades, or student information.
- Excessive retention of deleted-account data.
- Insecure handling of backups and exported records.
- Information disclosure through predictable identifiers or verbose responses.

Distinguish public client configuration from actual secrets. Do not report a Firebase client configuration value as a secret merely because it is visible in the browser; assess the associated access controls and exposure.

If a real secret is discovered, do not print it in the report. Identify its location safely and recommend the appropriate revocation or rotation procedure.

14. Dependency and Software Supply-Chain Security

Review:

- Known vulnerable direct and transitive dependencies.
- Vulnerable versions of Firebase and related SDKs.
- Package lifecycle scripts and suspicious installation behavior.
- Dependency confusion and package-name risks where relevant.
- Unpinned or unexpectedly changing CI dependencies.
- GitHub Actions with excessive permissions.
- Untrusted pull-request workflows.
- Exposure of deployment secrets to untrusted builds.
- Build artifact integrity and deployment provenance.
- Accidental publication of ".env" files, source maps, or private artifacts.
- Insecure preview deployments and environment separation.

Use supported dependency-audit tools and investigate the actual impact of each finding.

Do not perform blind upgrades or introduce breaking changes simply to remove audit warnings.

15. Deployment, Hosting, and Configuration Security

Inspect the actual GitHub, Vercel, Firebase, and DNS-related configuration that is accessible and relevant.

Assess:

- Missing or incorrectly configured HTTP security headers.
- Content Security Policy quality.
- Clickjacking protections.
- MIME-sniffing protections.
- HTTPS and transport-security configuration.
- Cookie attributes if cookies are used.
- Cross-origin resource sharing (CORS), where relevant.
- Publicly accessible debug endpoints.
- Exposed development servers and preview deployments.
- Incorrect SPA routing and accidental exposure of sensitive files.
- Environment separation between development, preview, and production.
- Source-map and build-artifact exposure.
- CI/CD permission scope.
- Branch protection and deployment authorization.
- Unintended deployment triggers and unsafe rollback procedures.

Verify HTTP response headers against the actual deployed test environment when access is authorized. HTML meta tags are not substitutes for HTTP security headers.

Do not claim that hosting-provider settings are secure unless they were actually inspected.

16. Logging, Monitoring, and Incident Readiness

Assess whether security-relevant events are recorded appropriately, including:

- Failed privileged access attempts.
- Role changes and administrator actions.
- Unauthorized access attempts.
- Suspicious exam submission patterns.
- Certificate issuance and revocation.
- Account deletion and recovery.
- Rate-limit violations.
- Unusual resource consumption.

Check that logs do not expose passwords, tokens, API secrets, or unnecessary personal data.

Verify whether alerts, retention, and incident-response procedures exist. Clearly distinguish implemented controls from recommendations.

17. Chained Attacks and Adversarial Scenarios

Do not test vulnerabilities only in isolation.

Construct realistic, application-specific attack chains, such as:

- A compromised student account attempting to reach instructor functionality.
- A manipulated user profile combined with weak Firestore Rules.
- A leaked identifier combined with a missing ownership check.
- A client-side grading weakness combined with unauthorized result submission.
- An exposed certificate endpoint combined with predictable identifiers.
- A vulnerable dependency combined with an exposed reachable attack surface.
- A permissive upload rule combined with unsafe content rendering.
- A weak administrative workflow combined with missing audit protections.
- Repeated inexpensive requests combined with expensive downstream operations.

For each chain, document every required precondition, the security boundary crossed, the potential impact, and the controls that prevent or fail to prevent exploitation.

Do not assume a chain is exploitable simply because its individual components exist. Validate the relevant conditions safely.

Full-Spectrum Vulnerability Assessment, Penetration Testing, Attack Simulation & Production Security Validation

1. المهمة الأساسية

وسّع المرحلة الثالثة لتصبح مراجعة أمنية شاملة للتطبيق الحالي ASIRA Research Learning Platform، تغطي أكبر نطاق عملي من الثغرات والهجمات الحديثة، مع التركيز على حماية حسابات المستخدمين وبيانات الطلاب والاختبارات والدرجات والشهادات وحسابات المدرسين والإدارة.

لا تكتفِ بمراجعة الكود أو تشغيل أدوات الفحص الآلي. نفّذ اختبارات أمنية فعلية وآمنة ضمن النطاق المصرح به، واستخدم نتائجها لتحديد الثغرات القابلة للاستغلال والتحقق من الإصلاحات.

شروط إلزامية:

- افحص المشروع وتقنياته وخدماته الفعلية قبل تحديد الاختبارات.
- لا تعِد بناء التطبيق ولا تحذف ميزاته أو تغيّر بنيته دون ضرورة مثبتة.
- لا تفترض أن وجود حماية في الواجهة يعني وجود حماية في قاعدة البيانات أو الخادم.
- اختبر الصلاحيات مباشرة، وليس من خلال الواجهة فقط.
- استخدم بيئة اختبار معزولة أو Firebase Emulator للاختبارات التي قد تغيّر البيانات.
- لا تنفذ هجمات إغراق أو اختبارات تدميرية على الإنتاج.
- لا تستهدف أنظمة أو حسابات أو خدمات خارج النطاق المصرح به.
- لا تعرض الأسرار أو بيانات الطلاب الحقيقية في التقارير.
- لا تعتبر أي ثغرة مغلقة قبل إعادة اختبارها وإثبات نجاح الإصلاح.
- لا تدّعِ اختبار أي فئة لمجرد إدراجها في هذه الخطة.

2. اختبارات حجب الخدمة واستنزاف الموارد

اختبر صراحةً الفئات التالية، مع مراعاة اختلاف أساليب الهجوم وآليات الحماية:

A. DoS — Denial of Service

- استنزاف موارد التطبيق بطلبات متكررة.
- استنزاف الذاكرة أو المعالجة بسبب مدخلات أو عمليات مكلفة.
- إرسال طلبات أو ملفات أو مستندات بأحجام غير متوقعة.
- استغلال الاستعلامات المكلفة أو غير المحدودة.
- التسبب في بطء الوظائف الأساسية أو فشلها.
- استغلال العمليات التي تستغرق وقتًا طويلًا أو تتكرر دون حاجة.

B. DDoS — Distributed Denial of Service

- تقييم مدى تعرض الخدمات لهجمات موزعة من مصادر متعددة.
- التحقق من وجود حماية مناسبة لدى مزود الاستضافة، إذا كانت متاحة للفحص.
- مراجعة حدود الطلبات والموارد وإعدادات الحماية والمراقبة.
- تحديد ما إذا كانت الحماية تعتمد على التطبيق وحده أم على البنية التحتية أيضًا.

لا تنفذ هجوم DDoS فعليًا أو ترسل حركة مرور ضخمة إلى الإنتاج. اختبر ضوابط التطبيق بأحمال محدودة في بيئة معزولة، وافحص إعدادات المزود والأدلة المتاحة، وسجّل أي جانب لا يمكن التحقق منه.

C. Resource Exhaustion and Cost Abuse

- استنزاف حصص Firestore وCloud Functions والخدمات الخارجية.
- تكرار عمليات القراءة والكتابة والاستعلامات المكلفة.
- إساءة استخدام إرسال الإشعارات والبريد والتحقق من الشهادات.
- إنشاء طلبات تؤدي إلى استدعاءات متكررة لخدمات مدفوعة.
- استغلال حلقات غير محدودة أو وظائف يمكن استدعاؤها دون قيود كافية.
- تقييم مخاطر تضخم الفواتير أو استنفاد الحصص المجانية.

D. Rate-Limit Bypass

- التحقق من إمكانية تجاوز حدود الطلبات بتغيير الحساب أو تكرار الجلسات أو استخدام مسارات بديلة.
- التحقق من تطبيق الحدود على الوظائف الحساسة وليس الواجهة فقط.
- فحص وجود حدود مناسبة لتسجيل الدخول والاختبارات ورفع الملفات وإصدار الشهادات.

لكل اختبار، حدّد آلية الحماية المطلوبة، ونفّذ اختبارًا محدودًا وآمنًا حيثما أمكن، وسجّل النتيجة والأدلة.

3. هجمات الحسابات والمصادقة

اختبر صراحةً:

- Brute-Force Attacks: تخمين كلمات المرور.
- Credential Stuffing: تجربة بيانات دخول مسربة.
- Password Reset Abuse: إساءة استخدام استعادة كلمة المرور.
- Account Enumeration: كشف وجود الحسابات.
- Session Hijacking: الاستيلاء على الجلسات، حيث ينطبق.
- Token Theft and Replay: إساءة استخدام الرموز أو إعادة إرسالها.
- Authentication Bypass: تجاوز التحقق من الهوية.
- Account Takeover: الاستيلاء على الحسابات عبر مسارات الاستعادة أو التحقق الضعيفة.
- Weak Session Invalidation: استمرار الصلاحيات بعد تعطيل الحساب أو تغيير دوره.
- Insecure Account Recovery: ضعف إجراءات استعادة الحساب.
- Unauthorized Account Creation: إنشاء حسابات أو هويات بطرق غير مصرح بها.
- Email Verification Abuse: استغلال تدفقات التحقق من البريد.

تحقق من سلوك التطبيق عند حذف الحساب، وتعطيله، وتغيير كلمة المرور، وسحب صلاحيات المستخدم.

افحص تحديدًا ما إذا كانت الجلسات والرموز القديمة تتيح الاحتفاظ بصلاحيات لم تعد مستحقة.

- Public Exposure of Private Files.
- Trust in Client-Supplied UIDs or Roles.
- Client-Side Authorization Without Database Enforcement.
- Abuse of Firebase Callable or HTTP Functions، إذا كانت موجودة.
- Improper Trust in Custom Claims or Stale Authorization State.

اختبر القواعد من خلال Firebase Emulator واكتب اختبارات آلية تغطي السماح والمنع لكل دور.

لا تعتبر نجاح اختبارات البناء دليلًا على أمان Firestore Rules.

- تجاوز توقيت الاختبار أو موعد إتاحته.
- إعادة إرسال إجابة أو طلب سابق.
- إرسال محاولات متزامنة لتجاوز القيود.
- انتحال هوية طالب عند تسليم الإجابات.
- تعديل حالة إكمال الدورة.
- تزوير حالة النجاح أو استحقاق الشهادة.
- تزوير أكواد الشهادات أو تخمينها.
- إصدار شهادة دون استيفاء المتطلبات.
- إعادة تفعيل شهادة ملغاة.
- اختلاف نتيجة التحقق العام من الشهادة عن السجل الحقيقي.
- تعديل سجل المحاولات أو التغذية الراجعة.
- الوصول إلى إجابات أو درجات طالب آخر.

تحقق من أن احتساب الدرجات والتحقق من استحقاق الشهادات يتمان في موضع موثوق، وليس اعتمادًا على بيانات يرسلها العميل دون تحقق مستقل.

7. هجمات الحقن وتنفيذ المحتوى الضار

اختبر جميع أنواع الحقن التي تنطبق على التقنيات المستخدمة:

- Reflected XSS.
- Stored XSS.
- DOM-Based XSS.
- HTML Injection.
- JavaScript Injection.
- NoSQL Injection، حيث ينطبق.
- SQL Injection، إذا كانت هناك قاعدة بيانات SQL.
- Command Injection، إذا كانت هناك عمليات تنفذ أوامر نظام.
- Template Injection، إذا كانت هناك محركات قوالب مناسبة لهذا النوع.
- Path Traversal.
- Local File Inclusion / Remote File Inclusion، إذا كان التصميم يسمح بهما.
- Prototype Pollution.
- Unsafe Deserialization.
- Open Redirect.
- Unsafe URL Schemes.
- HTML/SVG Injection.

افحص المدخلات التي تظهر في أسماء المستخدمين، وأوصاف الدورات، والإعلانات، والتعليقات، والتسليمات، والملفات، ورسائل النظام.

اختبر أيضًا نقاط استخدام HTML غير الآمن وعمليات DOM التي قد تسمح بتنفيذ محتوى أدخله المستخدم.

استخدم مدخلات اختبار غير ضارة، وأثبت ما إذا كان المحتوى يُعرض كنص آمن أم يُفسر ككود.

8. SSRF وCSRF والهجمات المرتبطة بالطلبات

SSRF — Server-Side Request Forgery

- افحص أي وظيفة تجلب روابط أو موارد يحددها المستخدم.
- تحقق من قيود البروتوكولات والوجهات وإعادة التوجيه.
- اختبر في بيئة معزولة باستخدام نقاط اختبار آمنة.
- لا تستهدف عناوين الخدمات الداخلية أو بيانات تعريف السحابة أو الأنظمة الخارجية دون تصريح صريح.

CSRF — Cross-Site Request Forgery

- تحقق مما إذا كان أسلوب المصادقة يسمح بتزوير الطلبات عبر المواقع.
- افحص الطلبات التي تغير البيانات أو الأدوار أو الدرجات.
- قيّم الحاجة إلى رموز CSRF أو ضوابط Origin/SameSite المناسبة للبنية الفعلية.

HTTP Request Abuse

- HTTP Parameter Pollution.
- Request Replay.
- Duplicate Request Abuse.
- Content-Type Confusion.
- Host Header Injection، حيث ينطبق.
- CORS Misconfiguration.
- HTTP Method Misconfiguration.
- Request Smuggling، فقط إذا كانت البنية الفعلية تتيح اختبارًا مناسبًا ومصرحًا به.

لا تصنّف أي فئة على أنها ثغرة مؤكدة دون دليل على انطباقها وقابلية استغلالها.

14. إساءة استخدام وظائف المنصة

- إرسال دعوات أو إشعارات بصورة مفرطة.
- استنزاف عمليات البحث والتصدير.
- استغلال عمليات النسخ الاحتياطي والاستعادة.
- الوصول إلى وظائف إدارية مخفية.
- تجاوز شروط الالتحاق بالدورات.
- تغيير التقدم الدراسي مباشرة.
- التلاعب بسجلات النشاط.
- استغلال اختلاف الحالة بين الواجهة وقاعدة البيانات.
- تكرار عمليات مكلفة أو غير محدودة.
- إساءة استخدام عمليات إصدار الشهادات والتحقق منها.

لا تكتفِ بفحص كل وظيفة منفردة؛ افحص أيضًا إمكانية دمج عدة نقاط ضعف للوصول إلى أثر أمني أكبر.

15. تحليل سلاسل الهجوم المركبة

أنشئ سيناريوهات هجومية واقعية خاصة بمنصة ASIRA، مثل:

1. طالب يغيّر معرف سجل للوصول إلى درجات طالب آخر.
2. مستخدم يعبث ببيانات ملفه لمحاولة اكتساب دور إداري.
3. تجاوز قواعد الواجهة ثم محاولة الوصول مباشرة إلى Firestore.
4. استغلال ضعف احتساب الدرجات لإرسال نتيجة غير مستحقة.
5. الجمع بين رفع ملفات غير مقيد وعرض محتوى غير آمن.
6. الجمع بين غياب حدود الطلبات وعمليات مكلفة لاستنزاف الموارد.
7. استغلال إعداد نشر ضعيف للوصول إلى معلومات حساسة.
8. الاستفادة من جلسة قديمة بعد إلغاء الصلاحيات.
9. الجمع بين تسريب بيانات وغياب التحقق من ملكية السجل.
10. إساءة استخدام وظيفة إدارية عبر حساب مخترق محدود الصلاحيات.

هذه أمثلة وليست افتراضات بوجود ثغرات. اختبر السيناريوهات المنطبقة فقط، ووثّق المتطلبات والأدلة والنتائج.
